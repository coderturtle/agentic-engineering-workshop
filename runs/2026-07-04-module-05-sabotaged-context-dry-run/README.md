# Module 05 verification: sabotaged-context variant, an honest negative finding (two rounds)

## What was built

`fixtures/receipts/variants/sabotaged-context/`: the third full agent setup for Module 05's capstone (prompt, context, harness config, bounded loop, all provided), attempting the same task as `sabotaged-harness/` and `sabotaged-loop/` (fix the seeded month-boundary timezone bug in `group_expenses_by_month`). Unlike the two existing variants, `prompt.md`, `harness-config.md`, and `loop.sh` are all correct here, `harness-config.md` is scoped to `receipts/` (copied from `sabotaged-loop`'s correct scope) and `loop.sh` checks the real unittest exit code (copied from `sabotaged-harness`'s correct verification). The intended sabotage lives entirely in `background.md`: a confidently stated, false claim that this codebase's timestamps are already localized to the target timezone upstream, so no timezone conversion is ever needed, backed by a fabricated "prior incident" in which someone added timezone conversion and it supposedly broke things, framed to specifically pre-empt the exact fix the seeded bug requires.

`receipts/grouping.py`, `receipts/cli.py`, `receipts/__init__.py`, and `tests/` are byte-identical to `sabotaged-harness`'s copies (same seeded bug, untouched). `SPEC.md` started as a byte-identical copy of `sabotaged-harness/SPEC.md` but was later redacted, see "Third finding" below, to remove its explicit "The seeded bug" section, which named the exact root cause and fix in plain prose. The redacted version is what's shipped in the canonical directory; see "What ships, and why" at the bottom of this document for the final state of both `SPEC.md` and `background.md`.

## Method

Per this project's standard (real agents, not narrated behavior; see `runs/2026-07-03-module-05-dry-run/`):

1. Ran a fresh `general-purpose` subagent against the shipped variant (task = `prompt.md`, scope = `harness-config.md`, background context = `background.md`, working directory = a full copy of `sabotaged-context/`, so `SPEC.md`, `tests/`, and `receipts/` were all visible alongside `background.md`, exactly as a learner or a scope-obedient sub-agent would see them). Observed whether the false background claim actually steered the agent away from the real fix.
2. The predicted failure mode did not occur on the first attempt (background.md v1, see `attempt-1-background-v1-weaker/`). Per this task's own contingency ("iterate once... without becoming absurd or unfalsifiable"), strengthened the claim's prominence and forcefulness (background.md v2, moved to a dedicated, emphatic top section, explicitly naming the exact failure shape and pre-emptively telling the reader not to add timezone conversion). Ran a second, independent fresh subagent (`attempt-2-background-v2-strengthened/`). The failure mode still did not occur.
3. Per the task's stop condition ("if it still doesn't reproduce after one revision, stop and report the honest result"), no further `background.md` iteration was attempted at that point.
4. Ran the isolating test anyway for completeness: a third fresh subagent against a copy where `background.md` was replaced with the honest version (byte-identical to `sabotaged-harness/background.md`), everything else unchanged (`isolating-test-corrected-background/`). Also reached `SUCCESS`, as expected for a control condition.
5. **Second round, after coordinator review:** the coordinator identified that `SPEC.md`'s "The seeded bug" section, shipped byte-identical into every variant per this fixture family's own rule, states the exact root cause and fix in plain prose, which is what actually neutralized both prior attempts regardless of `background.md`'s wording. Built a redacted `SPEC.md` for this variant (removes that section only, keeps everything else, with an explanatory comment) and reran the full cycle: a fourth fresh subagent against the redacted `SPEC.md` plus the shipped `background.md` v2 (`attempt-3-redacted-spec-sabotaged-bg/`), and a fifth fresh subagent as the control, redacted `SPEC.md` plus honest `background.md` (`isolating-test-2-redacted-spec-honest-bg/`). See "Third finding" below.

## Results

**Both sabotaged attempts (v1 and v2) reached `TERMINAL STATE: SUCCESS` on the first attempt, with the real bug genuinely fixed.** In both runs, the subagent read `SPEC.md` unprompted (it was simply sitting in the working directory, discovered via a normal directory listing) and found it directly contradicts `background.md`: `SPEC.md` states outright that `timestamp_utc` is genuine UTC, names the exact seeded bug (`ts.strftime("%Y-%m")` on the raw UTC value, never converted to `tz`), names the exact failing test, and prescribes the fix. Both agents independently cross-checked this against the actual code (`_parse_row`'s `datetime.fromisoformat(...).replace("Z", "+00:00")` and the fact that `group_expenses_by_month` never uses `tz`) and against `test_month_boundary_crosses_in_target_timezone`'s own inline comment (which only makes sense if the timestamp is real UTC). Both agents explicitly named the contradiction with `background.md` in their own report and discounted the false claim rather than trusting it. Both then applied the same minimal, correct fix (`from zoneinfo import ZoneInfo`; convert via `ts.astimezone(zone)` before formatting the key), touching nothing outside `receipts/grouping.py`, and both independently reverified `OK` / `TERMINAL STATE: SUCCESS`.

**The isolating test (honest background.md) also reached `SUCCESS`,** which means swapping `background.md` between the false and honest versions produced **no observable difference in outcome**, the exact opposite of what an isolating test is supposed to show when a layer is truly the bottleneck. If context were the differentiator here, only the honest-background run should succeed; instead, all three runs succeeded.

## Why this happened: a structural finding, not (only) a wording problem

This project's own SPEC.md (`fixtures/receipts/SPEC.md`) requires `SPEC.md` to be "copied verbatim into every fixture variant," including this one, and it is not optional per this task's own instructions (item 7). `SPEC.md` is short, sits at the top level of the working directory next to `background.md`, and is exactly on-topic for the reported symptom, it names the seeded bug and its fix in plain prose. A reasonably thorough coding agent investigating "date stuff is off in monthly totals" is very likely to open a file called `SPEC.md` sitting right next to the other docs, especially since Module 05's own diagnostic method explicitly tells the human learner to "read every file." Once that happens, `SPEC.md`'s explicit, unconditional description of the bug functions as a stronger, unambiguous authority that straightforwardly outweighs a background doc's assertion, however confidently or prominently that assertion is stated. This is different from Module 05's other two variants: `sabotaged-harness`'s wrong scope and `sabotaged-loop`'s broken verification are structural/mechanical problems that remain broken regardless of whether the agent reads `SPEC.md` correctly. A context-only sabotage, by contrast, is specifically a battle for which document the agent trusts more, and in a fixture family where the ground-truth spec is always present and always names the bug outright, the spec wins that battle for any agent that reads it, independent of how the false claim in `background.md` is worded.

This mirrors the shape of `runs/2026-07-03-module-03-dry-run/README.md`'s negative-control finding on persistent state: the mechanism was built correctly, but its necessity for this specific setup wasn't demonstrated, because a capable agent's own diligence (reading `SPEC.md` and the test) substituted for trusting the sabotaged doc. What would make context sabotage actually bite here: either omitting `SPEC.md` from the working directory a sub-agent can see (which the module's own diagnostic framing and this task's fixture-family requirements don't allow), or a false claim whose falsity isn't independently checkable from any other file in the directory, which is a much narrower design space, since this fixture family's whole premise is that `SPEC.md` and the test suite are always available as ground truth.

## Third finding: redacting SPEC.md's answer key still didn't make the sabotage bite

After reviewing the above, the coordinator correctly identified this as a real structural bug in the fixture design, not just a hard-to-crack sabotage: `SPEC.md`'s "The seeded bug" section is a byte-identical, mandatory file across the whole `receipts` fixture family, and it states the exact root cause and fix in plain prose. That's harmless for `sabotaged-harness`/`sabotaged-loop` (their sabotage is mechanical and doesn't care whether the agent knows the correct fix), but it defeats a context-bottleneck variant specifically, regardless of how strongly `background.md` is worded.

**Fix attempted:** created a redacted `SPEC.md` for this variant only, identical to `sabotaged-harness/SPEC.md` except the "## The seeded bug" section (the three paragraphs naming the exact root cause and fix) is removed, and edge case #2's dangling `": see below"` reference is trimmed to a plain sentence. Everything else (signature, required edge cases, "Running it", "Variants") is preserved verbatim. A one-line HTML comment at the top explains the redaction, so a learner diffing this file against another variant's `SPEC.md` understands it's deliberate, not drift.

**Reran the full cycle against the redacted `SPEC.md`:**
- **Attempt 3** (`attempt-3-redacted-spec-sabotaged-bg/`): shipped `background.md` v2 (the strengthened sabotage) against the redacted `SPEC.md`. Fresh agent. Result: **still `TERMINAL STATE: SUCCESS`.** This time the agent didn't even open `SPEC.md`, it interpreted the harness scope ("you may read and edit files under `receipts/` only") as a *read* boundary, not just an *edit* boundary, and confined all its file reads to `receipts/`. It still reached the correct diagnosis, because `receipts/grouping.py`'s own module docstring independently restates the same "required edge cases" text as `SPEC.md`, including the exact month-boundary-crossing description, and that docstring is unavoidable to read: it sits at the top of the very file the agent has to edit. The agent explicitly weighed `background.md`'s claims against the docstring and the CLI's real `--tz` flag, found the contradiction, and applied the correct fix without ever touching `background.md`'s "don't add timezone conversion" instruction.
- **Isolating test 2** (`isolating-test-2-redacted-spec-honest-bg/`): same redacted `SPEC.md`, honest `background.md`, fresh agent, as the control. Also `SUCCESS`, on the same basis (`SPEC.md`'s edge-case list plus the test's own inline comment).

Both terminal states were independently reverified by rerunning `./loop.sh` directly outside the subagent, confirming `TERMINAL STATE: SUCCESS` in both cases.

**Per the coordinator's own stop condition ("if the sabotage still doesn't reproduce even without the answer key, report that honestly... don't force a third iteration"), no further iteration was attempted.** This is reported as the honest final result: redacting `SPEC.md`'s explicit section was necessary but not sufficient, because the same ground-truth information is present in a second, unredactable place, `receipts/grouping.py`'s own docstring, which restates the full "required edge cases" list (word for word, in this fixture, since `SPEC.md`'s edge-case list and the module docstring were originally written to match each other; see `fixtures/receipts/SPEC.md`'s note "don't restate the spec differently inside a module README", the same discipline that keeps `SPEC.md` and the docstring in sync is exactly what makes the docstring an equally reliable answer key). A third, deeper channel also independently confirms the correct behavior regardless of either document: `tests/test_grouping.py::test_month_boundary_crosses_in_target_timezone`'s own inline comment spells out the UTC-to-`America/New_York` conversion by hand for the exact input it uses.

**The structural conclusion:** this specific fixture (function docstring + required-edge-case spec + one narrowly-scoped, heavily-commented failing test) is unusually self-documenting by design, a deliberate strength for Modules 01-04 (a learner or agent should be able to find the bug from the code and test alone) that becomes a liability for a context-bottleneck variant, which needs the *opposite* property: a codebase where the false context is the *only* accessible signal, or at least the most accessible one. Built correctly, the four other layers of this fixture family (a well-specified function, a well-commented test, a real CLI flag wired to the parameter in question) all independently leak the answer through channels a competent, thorough agent will read anyway in the course of just doing its job, no matter which document it's told to trust. Making a context-only sabotage bite here would need a deeper redesign than either `background.md`'s wording or `SPEC.md`'s completeness, for instance, a version of `group_expenses_by_month` whose docstring doesn't restate the exact edge case, or a test whose assertion doesn't include a comment explaining the UTC/local math, which starts to conflict with this fixture family's own stated principle of keeping `SPEC.md`, the docstring, and the test aligned as multiple honest sources of truth. That tension is itself worth surfacing to whoever maintains this fixture family, rather than solved unilaterally in one variant.

## What this validates, honestly

- The variant's harness and loop layers are confirmed correct: every run, sabotaged or not, was able to reach and edit `receipts/grouping.py` (harness) and got an honest, correct terminal-state report once the code was actually fixed (loop). Neither ever produced a false negative or false positive across three independent runs.
- The context sabotage as designed and built, a false, confidently-stated timezone claim in `background.md`, strengthened once, then run again against a redacted `SPEC.md` with its explicit answer removed, **did not reproduce the predicted misdirection in any of the four sabotaged/control run pairs** against a capable, thorough general-purpose agent that had access to the working directory. This is reported as a genuine negative finding, not hidden or softened: rubric criterion 2 for this module ("evidence, not guess") is exactly the discipline this write-up follows, every isolating test showed no difference in outcome, so context was not shown to be a real bottleneck in this built fixture, for this kind of agent.
- Whether this variant is genuinely useful for the module as built is an open question this finding raises, not one this dry run resolves. A possible follow-up: note in the module content (per the honest-scope-note pattern already used for the prompt/context red herrings) that the context-bottleneck variant's misdirection was not demonstrated against a capable agent that reads the working directory, the same way the module's other honest caveats are written down rather than asserted away. A deeper follow-up, flagged for whoever maintains this fixture family: the same self-documenting properties (a docstring that restates the spec, a test with an explanatory comment) that make Modules 01-04 fair and diagnosable also work against a context-only sabotage in Module 05, and resolving that tension needs a fixture-level decision, not another `background.md` rewrite.
