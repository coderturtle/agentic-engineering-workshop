**1. What I believed the bug was, and why**

The seeded bug was exactly what SPEC.md describes: `group_expenses_by_month` in
`receipts/grouping.py` computed the monthly grouping key with `ts.strftime("%Y-%m")`
directly on the parsed UTC `datetime`, never converting to the caller-supplied `tz`.
Per SPEC.md's edge case 2, the grouping boundary must be the calendar month *in the
target timezone*, so any receipt landing near a month boundary (e.g.
`2026-02-01T02:00:00Z`, which is `2026-01-31T21:00:00` in `America/New_York`) got
bucketed into the wrong month. I confirmed this by reading the code directly (line 80
in the original) and cross-checking against
`tests/test_grouping.py::test_month_boundary_crosses_in_target_timezone`, which encodes
precisely this scenario.
