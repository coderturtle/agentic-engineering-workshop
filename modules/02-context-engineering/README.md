# Module 02: Context Engineering

## The question this module answers

What does the model actually need to see, and what should be left out?

## Where it sits in the arc

Second module, after prompt engineering. The shift here is from "write a good instruction" to "curate what the model can see": still a single-turn-adjacent concern, but about the window's contents rather than the instruction itself. Comes before harness engineering (module 03), which is about what the agent can *reach* across tool calls, not just what's in one window. See [modules/README.md](../README.md) for the full arc.

## Learning objectives

- Curate a context window to a fixed budget without losing what the task actually needs.
- Decide what to summarize, what to preserve verbatim, and what to exclude on purpose, and justify each decision.
- Recognize when a bad output is a context problem (wrong/missing information) rather than a prompt problem (bad instruction) or a harness problem (wrong tool access).

## Exercise material this module draws from

A context-budget exercise: a deliberately oversized/noisy context that must be curated down to a fixed budget while preserving what the task needs. This forces a real curation tradeoff instead of just discussing one in the abstract. (This module had no exercise anchor at all before the Workshop Review Panel's Instructional Designer flagged the gap; see `docs/review-panel/2026-07-03-initial-design.md`.)

**Cumulative hook:** the exact same task as Module 01, now buried in noise. You already hold a proven prompt from Module 01; this exercise lands hard precisely because of that. A perfect instruction still fails when the window is wrong or missing what it needs.

## Exercise: curate, then rerun Module 01's task inside it

Runs against `fixtures/receipts/variants/bloated/`: the Module 01 unimplemented variant, buried under 9,289 lines of noise (a padded README, a versioned CHANGELOG, an unrelated `legacy_export.py`, three stale docs, and a red-herring per-state tax-rate config), generated by `scripts/generate-bloated-variant.py`.

> Curate `fixtures/receipts/variants/bloated/` down to 2,000 lines or fewer (measured by `scripts/context-budget.sh`), then run Module 01's task again inside the curated context: a single prompt that implements `group_expenses_by_month` correctly, first try. It must still pass. Write a short justification: what you kept verbatim, what you summarized, what you cut, and why.

The post-curation task's correctness depends on including the right slice; the distractors live in the noise. `config/tax_rates.yaml` in particular is a genuine red herring: it looks like it could plausibly affect expense totals and is never read by anything the task depends on.

## Rubric

1. **Budget met (gate).** Assembled context is at or under 2,000 lines, measurably (`scripts/context-budget.sh`).
2. **Task still correct (gate).** Output passes the full test suite with the curated context, on the first try.
3. **Necessary inclusion (scored).** The specific lines the task depends on (the function under test, its signature, the spec) are present verbatim, not summarized away.
4. **Justified exclusion (scored).** The write-up names what was cut and why; nothing load-bearing was cut.
5. **Summarize-vs-verbatim judgment (scored).** Verbatim reserved for what must be exact; summary, if used at all, reserved for orienting material.
6. **No noise smuggled (scored).** The red-herring config and the unrelated module are excluded entirely, not trimmed and kept partially.

## Required to advance

Take `fixtures/receipts/variants/bloated/` down to the 2,000-line budget and still get Module 01's task right, with a short written justification of what you kept, summarized, cut, and why. Submitted curated context, the task output, and the justification, checked against the rubric above. Reading this module does not count: you advance on a working curation, not on having read this page.

## Takeaway

A context-budgeting Skill: your justification write-up, generalized into a personal checklist for "what to keep, what to cut, in what order" and packaged as a Claude Code Skill (or your harness's equivalent) you load in future sessions. The exercise produces a one-off curation; the takeaway is the reusable judgment behind it, made loadable. Reference implementation: `.claude/skills/context-budgeting/SKILL.md`, built from a real curation validated in `runs/2026-07-03-module-02-dry-run/`.

## Stop condition

Curated context at or under the 2,000-line budget, plus a passing output on the first try, plus a justification covering what was kept, summarized, and cut. **Alternate terminal:** if it cannot pass under budget, identify the single inclusion that would fix it. Diagnosing the missing piece is the skill, even if the curation attempt itself didn't succeed.

## Harness

Agnostic exercise, Claude-Code-leaning takeaway with a translation note. Curation is universal; only budget measurement and the Skill packaging touch tooling. `scripts/context-budget.sh` is a harness-neutral line/char counter usable from any tool; token-counting for a specific harness is a separate, per-tool concern the script deliberately doesn't try to replace. The Skill is shown in Claude Code's `SKILL.md` form; translate the checklist itself to whatever your harness's equivalent loadable-context mechanism is.
